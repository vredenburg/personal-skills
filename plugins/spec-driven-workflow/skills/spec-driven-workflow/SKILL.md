# Specification-driven development

This skill supplies a process, not project requirements or permission to act. Follow current human instructions, applicable repository policy and runtime restrictions. Inspect current changes and preserve unrelated work.

This skill is self-contained and works without the optional companion global instructions. Those instructions provide personal defaults across projects and guidance on when to use the skill. They require separate installation; installing or using this skill does not apply them.

## Choose the relevant guidance

- [Adoption](references/adoption.md): propose or apply an explicitly scoped workflow change.
- [Lifecycle](references/lifecycle.md): project direction, readiness, records and verification for delivery work.
- [Delegation and handoffs](references/delegation.md): assignments, integration and successor suggestions; use [model selection](references/model-selection.md) when selecting an agent.
- [Templates](assets/templates.md): optional record outlines, adapted to existing project formats.

Read only what the task needs. Reuse current guidance already in context and the project's own complete workflow; do not duplicate it into new files.

## Boundaries that apply throughout

Acceptance, authorization and verification are separate facts. Implementation needs accepted requirements and decisions, a proportionate plan and explicit scoped authorization, as defined in the lifecycle. Reuse existing approval; a single explicit user instruction can accept a scope and authorize it together. Neither skill adoption nor a passing review supplies implementation permission.

Installation, new tooling/skills/pipelines, provisioning, production assets, commits/pushes, deployment, publication and successor-chat creation or messaging need applicable explicit authorization. A review draft does not authorize installation or adoption.

During documentation-only work, describe future application tests and experiments in prose; do not create application code, executable application tests, manifests, infrastructure or production assets. Documentation and package validation remain appropriate. Surface conflicting accepted sources or proposed changes to commitments; continue independent authorized work while awaiting a necessary decision.
